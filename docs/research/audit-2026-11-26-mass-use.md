# Mass-use audit, 2026-11-26 (Marketo 1.4.3)

Five auditors (AI apps and models, MCP tool layer, long run times, Chrome runtime, data integrity), each checked by a skeptic that tried to refute every finding against the code. "confirmed" = the failing path was traced in code; "plausible" = the path exists but depends on outside behaviour (an AI app's defaults, a platform's markup). Nothing here is fixed yet.

Kept: 50. Refuted: 2.

## 1. [high / confirmed] An unreadable marketo-db.json at startup loads as an empty hub, then the first save overwrites both the file and the good .bak

- Where: `electron/store.ts:40` (Data integrity, profiles and multi-instance)
- Who: Any OS, any AI app. Triggers: power loss or a dead laptop battery during a run, a db file saved with a BOM (Notepad, or PowerShell 5.1 Set-Content -Encoding UTF8), antivirus holding the file when the scheduled task starts the app at login, or any exception in the migration code (for example a null field from an old version).
- Scenario: 1) persist() (lines 144-147) does writeFileSync(tmp) then renameSync and never fsyncs. Runs save on every like, so a power cut on NTFS can leave marketo-db.json zero-length or full of NUL bytes. 2) On the next start, init() wraps JSON.parse AND all the migration code (lines 41-53) in one try. Any error, EACCES/EBUSY from a lock included (only ENOENT is treated differently), leaves db = empty(). Unlike chromeImport.readDb, proxy.ts and main.ts:612, it never strips a BOM. 3) It copies the bad file to .corrupt-<ts> but never tries marketo-db.json.bak. 4) lastBak starts at 0, so the first persist() (the first like, touchLive or settings change) copies the bad file over .bak (line 139) and then renames an empty db over the main file. Every account, warm-up date, reel, session and post log is gone. Today's action counts are gone too, so the next run sees zero likes/follows/posts today and does a full day's quota a second time: restriction risk.
- Fix: Strip the BOM. Retry transient EBUSY/EPERM/EACCES reads. Parse only inside the first try, and fall back to .bak (then the newest .corrupt) before going empty. Run migrations in their own try that keeps the raw data. When init went empty because of a bad file, never overwrite .bak. fsync the tmp file before the rename.
- Skeptic: store.ts:40-63 wraps readFileSync, JSON.parse and all migration in one try. Any non-ENOENT failure (a zero-length or NUL file after a power cut, EBUSY or EACCES from a lock at login, a BOM, a throw inside the migration) leaves db = empty(). The bad file is copied to .corrupt-<ts>, but nothing ever reads marketo-db.json.bak (grep finds no reader). lastBak starts at 0, so the first persist() (touchLive's saveLive is forced on its first call because lastLivePersist is 0) copies the bad file over .bak at line 139, then renames the empty db over the main file at 147. For a truncated file, .corrupt holds garbage too, so accounts, warm-up dates and today's counts are all gone. Triggers are uncommon per user but certain to happen to some users at mass scale.

## 2. [high / confirmed] Non-English UIs: browser_type/browser_press skip the language gate, so comments and DMs sent with Enter are uncounted, uncapped and unchecked

- Where: `electron/browser.ts:2558` (Chrome bridge and browser runtime)
- Who: Any AI app or model, for users whose Instagram, TikTok, Facebook or Pinterest UI is not in English (Spanish, German, Portuguese, Italian and so on). Weaker models that go straight to browser_type with submit are most likely to hit it.
- Scenario: 1) The user's Instagram is in Spanish. The comment textarea is named 'Agrega un comentario...'. 2) The AI calls browser_type(ref, text, submit:true). toolType calls inputBlock(tab, a, '') with an empty lang (lines 2558 and 2638), so the 'showing in es, buttons stay locked' refusal at line 1482 never runs. 3) The box name does not match /comment|reply/ or /message/ (line 2581), so the human-text check is skipped. 4) submitWithEnter -> classifyEnter (1260-1266): the name does not match, and f.multiline is true for a textarea or contenteditable, so the verdict is 'free'. Enter is pressed without approve(), so there is no checkAllowed('comments'), no per-thread cap, no humanText check and no recordAction. 5) The identity check is also English-only: whoami() in pageScript.ts:111-113 looks for 'Profile' or "'s profile picture", so signedInAs is never set and igUserId is never saved, and comments can go out from whatever account is signed in. The result is unlimited comments and DMs at bot speed, which is a direct restriction risk. Focus.lang is already collected (pageScript.ts:635) but never used.
- Fix: Pass the real language to inputBlock in toolType, toolPress and the attach tools: read it from the target (t.lang), or from window.__mk.focus().lang in submitWithEnter. Also make classifyEnter fail closed: on social sites, treat an unrecognised editable multiline box with text as 'comment' rather than 'free'.
- Skeptic: The path is real. toolType (browser.ts:2558) and toolPress (2638) call inputBlock(tab, a, ''), so the non-English refusal (1482 / netBlock 1461) never runs for them. Only toolClick passes t.lang (2333), and snapshots are not gated either. On a Spanish Instagram or TikTok, the comment box name does not match /comment|reply/ or /message/ (2581), so the humanText pre-check is skipped. browser_type does its own mouseClick, so no gated browser_click is needed. classifyEnter (1260-1266) returns 'free' because f.multiline is true for a TEXTAREA or contenteditable (pageScript.ts:629), and submitWithEnter (2536-2538) presses Enter with no approve(): no checkAllowed, no thread cap, no humanText check, no recordAction. Focus.lang (pageScript.ts:635) is collected but never read. whoami (pageScript.ts:111-113) matches only English 'Profile' and "'s profile picture", so signedInAs and igUserId (saved only at 1636 when snap.me matches) never get set. This hits every non-English user whose AI comments with submit:true, and Enter-to-send is the natural move once clicks are refused.

Nobody sets tool_timeout_sec anywhere, including Kip. On cancel, host.ts 113-127 never passes signal to MAIN_HANDLERS, and nothing listens for mcp:cancel. The 60 s default and the approval behaviour are Codex's own and cannot be checked from this code, so plausible. If it holds, scheduled runs fail for every Codex/ChatGPT user, which is why it stays high.

## 5. [high / plausible] Codex/ChatGPT (60 s) and Gemini CLI (10 min) MCP tool timeouts are never raised, and the hub ignores cancels, so long tools fail and then lock out retries

- Where: `electron/mcp/clients.ts:241` (Long run times, scheduling and dates)
- Who: Anyone whose autopilot or Kip uses Codex or ChatGPT desktop (Codex's default tool_timeout_sec is 60 s). Gemini CLI users hit it on very long tools (10 min default). Worst on slow PCs.
- Scenario: 1) tomlBlock (clients.ts:241) writes [mcp_servers.marketo] with no tool_timeout_sec. Kip's codexServers (kipEngines.ts:153-157) adds no timeout either. 2) The autopilot `codex exec` calls render_reel. ElevenLabs narration plus canvas encoding of a 30-60 s reel takes longer than 60 s, and so do browser_attach_reel/Post (25-40 s settle, plus up to UPLOAD_HOLD_MS of 5 min on FB/Threads), save_clip, record_screen, narrate_long_video and render_kip. 3) Codex marks the call failed after 60 s and sends a cancel. host.ts:126 forwards 'mcp:cancel', but nothing in src/ or preload listens for it, so the render keeps going and keeps useApp.job set. 4) The model retries render_reel and gets 'A render is already running' (src/state/store.ts:162), so it gives up or makes another reel. The finished MP4 is never posted, and runs post little or nothing.
- Fix: Write tool_timeout_sec (for example 1800) into the Codex TOML block and Kip's -c flags, and set the matching timeout in Gemini's settings entry. Handle 'mcp:cancel' in the preload/renderer by calling cancelCurrentRender, or let a repeated render_reel attach to the job already running and return its result.
- Skeptic: Code side is confirmed. tomlBlock (clients.ts:241) and codexServers (kipEngines.ts:150-158) never set tool_timeout_sec. host.ts:126 sends 'mcp:cancel', but preload.ts (lines 208-222) only listens for 'mcp:call', so nothing receives the cancel and the render keeps running. renderReel then throws 'A render is already running' while useApp.job is set (src/state/store.ts:162). The one part I cannot check from the code is the outside behaviour: Codex's 60 s default tool timeout and the fact that it does not reset on progress messages. render_reel, browser_attach_* with its settle/upload hold, and record_screen can easily run past 60 s. That would hit every Codex/ChatGPT autopilot or Kip user.

- Where: `electron/browser.ts:2621` (Chrome bridge and browser runtime)

## 7. [medium / confirmed] Session detail grows without limit: every like rewrites the whole JSON db synchronously and pushes the whole db to the window

- Where: `electron/store.ts:786` (Data integrity, profiles and multi-instance)
- Who: Users with many accounts/platforms who leave the app running for weeks, the mass-growth setups. The archive is off by default (shared/perf.ts:90 keepActivityDays: 0), and so is batched saving (batchSaveSec: 0).
- Scenario: Each like, follow, save or watch appends a SessionItem (url, creator, actions, note) and calls saveLive(true). That runs persist(), a synchronous JSON.stringify plus writeFileSync of the entire db on the main thread, plus a copyFileSync of the whole file to .bak once a minute. Every listener also gets the whole db, and pushDb (main.ts:122) structured-clones it to the renderer up to 4 times a second. Example: 10 accounts x 5 platforms x ~200 counted actions a day is about 10k items/day. After a month the db is tens of MB, so each click blocks the main process (MCP replies, Chrome bridge, IPC) for hundreds of ms. threadSends/recentTexts also scan every session. Runs slow down, time-limited runs get less done, and the UI stutters.
- Fix: Turn activity archiving on by default (for example 30 days) or archive items past N per session automatically. Also cap db.accounts snapshots. Longer term, move sessions out of the single JSON (per-day files) and send the renderer diffs instead of the whole db.
- Skeptic: recordAction pushes one SessionItem per counted action and calls saveLive(true), which runs persist(): a synchronous JSON.stringify and writeFileSync of the whole db on the main thread, plus a once-a-minute copy to .bak. Every listener then gets the whole db, and pushDb sends it to the renderer. The only trimming is archiveActivity, gated on keepActivityDays > 0, which defaults to 0 (shared/perf.ts:90). batchSaveSec also defaults to 0, and no other cap on sessions or items exists. The db therefore grows without bound and save cost grows with it. It hurts heavy multi-account users who keep the app for months.

## 11. [medium / confirmed] run.cmd has no per-run watchdog (run.sh does): a hung AI eats the whole task budget, and killed runs can leave orphaned AI processes still driving Chrome

- Where: `electron/autopilot.ts:243` (Long run times, scheduling and dates)
- Who: Windows users (most users). Worst with several profiles in one window (sequential runs) or with weaker models that loop.
- Scenario: 1) On macOS each AI gets `( sleep LIMIT_MIN*60; kill -TERM $PID )` (lines 343-350). On Windows the AI line (243) is a plain `type prompt | claude ...` with nothing like that. 2) With 3 profiles in one window, taskLimitMin is 90*3+10 = 280 min (line 475). If profile 1's AI hangs for 280 min, profiles 2 and 3 never run. 3) When Task Scheduler hits ExecutionTimeLimit it stops the task's own process (powershell.exe -> run.cmd). The piped claude/codex child is not killed by the script, so it can keep running with Chrome. The hub treats the run as over (stale flag, no live report), so tickExtra or the next trigger can start a second AI on the same accounts: double posts, double engagement, ban risk.
- Fix: Give each AI line in run.cmd and run-part-*.cmd its own watchdog: start the AI through a PowerShell wrapper that uses Start-Process -PassThru plus Wait-Process -Timeout (LIMIT_MIN*60), then `taskkill /T /F /PID` on timeout. Or launch the task action under a job object with kill-on-close.
- Skeptic: run.cmd's AI line (autopilot.ts:243) is a plain foreground pipe with no watchdog, while run.sh has the sleep/kill watchdog (lines 343-350). The only Windows limit is ExecutionTimeLimit = LIMIT_MIN*n+10 (line 475), so one hung or looping AI in a sequential multi-profile run uses up the time the later profiles needed. Whether child processes survive when Task Scheduler stops the task depends on Windows, but the missing per-AI limit is in the code. It mostly hurts multi-profile Windows users. Single-profile runs are still capped at 100 min.

## 13. [medium / confirmed] Any posted_at value is accepted, so a date-only, wrong-year or wrong-time-zone posted_at turns off the post-spacing gap

- Where: `electron/mcp/tools.ts:1547` (MCP tool layer under sloppy or weaker models)
- Who: All AI apps, mostly weaker models and models unsure of today's date. log_posts invites this, because its posted_at description says 'ISO date or YYYY-MM-DD'. Users far from UTC are affected even with exact times. X text posts and images, which are logged through log_posts, are the usual path.
- Scenario: The iso schema (line 235) is a plain z.string() with no format check. mark_posted stores a.posted_at as given (1547 -> store.markPosted -> linkPatch and logPosts), and log_posts does the same (1899). checkGap (browser.ts 1375-1393) takes the newest confirmed time from those values and ignores future ones (n <= now+60s). Example: the model posts an X text post at 15:00 and logs posted_at '2026-11-26', which parses to 00:00 UTC. It could also use its training-cutoff year, or a local clock time with 'Z' appended. lastConfirmed is then hours old, or in the future and dropped, so only the unconfirmed-click hold is left: min(15, gap) minutes (line 1391). After 15 minutes the hub allows the next X post, although the user set 90 minutes. That is the back-to-back posting the user rejected, and an automation signal. - Who: Any AI app. Triggered by an extension reload (the hub asks for it after an update, and the error texts tell users to reload), Chrome restarting, the helper re-targeting a window in multi-instance mode, or the pipe dropping after sleep
- Scenario: onChromeEvent 'gone' deletes every Tab for that conn (455), and ensureTab deletes the entry when tab.conn differs from the new conn (594-597). This drops settleUntil, lastCounted/streak, lastMove/lastPost and menuPost. Effects: 1) During a Facebook/Threads upload hold, a reconnect removes the 'post is still going up' guard (withTab 1744, toolClose, closeRunTabs), so the next browser_open url or the run-end clean-up closes or navigates the tab and the upload is lost. This is the exact loss the hold was added for. 2) The first like after reconnect skips engagePause (since = now - 0) and readFirst (lastCounted 0), so a burst can follow, which is what the Threads checkpoint comments warn about. The comment at line 187 says entries are kept 'so its pacing carries over'.
- Fix: Key pacing and settle state by account+site in a map that survives the Tab object, or on 'gone' mark the tab closed instead of deleting it, and re-bind it to the new conn when it connects again.
- Skeptic: The state is dropped as described: onChromeEvent 'gone' deletes the Tab (455), and ensureTab deletes it on a conn mismatch (594-597). After that, engagePause's since = now - 0 skips the pause (680-687) and readFirst skips its check, but only for the first counted action. That is one action, not a burst. Losing settleUntil matters only if the upload survives the reconnect while Marketo then navigates the tab. On an extension reload the old tab is orphaned instead (finding #8), so it is not navigated. Chrome restarts or sleep usually kill the upload anyway. Real but narrow.

## 47. [low / plausible] Auto-opening a picked Chrome profile waits only 30s, then fails at once for 120s (and never within 20s of hub start)

- Where: `electron/browser.ts:471` (Chrome bridge and browser runtime)
- Who: Slow PCs and laptops just woken from sleep (HDD, antivirus scanning the Electron-as-Node helper), on unattended scheduled runs where the hub was just launched
- Scenario: chromeFor polls match() for 30 x 1s (471-476). On a cold start, Chrome has to start, its service worker has to spawn the native host (the full Electron binary run as Node), the host has to connect, the hello has to arrive, and dirOf() has to find the key on disk (misses are cached for 8s). That can take longer than 30s, and the call throws. On the AI's retry, openFor returns false because lastLaunch was under 120s ago (chromeBridge.ts:217), so it throws again immediately without waiting, even though Chrome is still coming up. Also, process.uptime() < 20 makes openFor refuse outright right after the hub starts. Runs stop early with 'that one is not open or not connected'.
- Fix: If a launch happened within the last 120s, keep waiting for the connection instead of throwing. Raise the wait (for example to 90s) and drop the uptime guard, or make it wait instead of refusing.
- Skeptic: chromeFor waits 30 x 1s (471-476), and openFor returns false for 120s after a launch and while uptime is under 20s (chromeBridge.ts:217), so a retry inside that window throws at once. But each retry first tries chrome.pick/match, so once Chrome finishes connecting the call succeeds. Only a cold start slower than 30s plus an AI that gives up early ends the run. Whether that happens depends on the machine.

## 48. [low / plausible] Synchronous reads of all Chrome profiles' files on the main thread, triggered by every extension tab event

- Where: `electron/chromeProfiles.ts:70` (Chrome bridge and browser runtime)
- Who: Multi run users with many Chrome profiles (the profile maker creates up to 50), on slow disks
- Scenario: Every extension 'tab' or 'state' event calls onChromeEvent -> broadcast -> statusAll -> match() for every account -> dirOf -> list(). list() re-reads Local State plus each profile's 'Secure Preferences' and 'Preferences' with readFileSync at most every 10s, and every hello forces a fresh read (chromeBridge.ts:316). For unplaced keys, dirOfKey also reads up to 8MB LevelDB files every 8s. With 30-50 profiles connecting at once, or tab URL changes during scrolling, the Electron main thread blocks on tens of MB of reads. MCP replies and the UI stall, and on HDD laptops CDP replies can come close to their timeouts.
- Fix: Make list()/hasExtension async and cache per file by mtime. Throttle broadcast(), and do not force list(true) on every hello.
- Skeptic: list() re-reads Local State and each profile's Secure Preferences and Preferences synchronously, but only when the 10s cache has expired (70-71). dirOfKey's LevelDB scan runs only for keys not yet placed, and misses are cached for 8s. So with 50 profiles that is at most one burst of several MB to tens of MB every 10s, not one per tab event. A main-thread stall only matters on slow disks with many profiles.

## 49. [low / plausible] Pinterest country domains (pinterest.es/.it/.jp/.com.mx ...) are treated as leaving the site

- Where: `resources/extension/background.js:51` (Chrome bridge and browser runtime)
- Who: Users or proxy exits in countries where Pinterest sends www.pinterest.com to a ccTLD not in the list

Whether Pinterest still redirects users to country domains such as .es, .it, .jp or .com.mx, rather than *.pinterest.com subdomains (which are covered), is outside behaviour that cannot be checked here. Pinterest is also optional.

## 50. [low / plausible] A db save whose rename fails (EPERM from antivirus) throws after a like/follow/post already happened; the AI then retries and toggles or duplicates it

- Where: `electron/store.ts:147` (Data integrity, profiles and multi-instance)
- Who: Windows users with Defender or a third-party antivirus, backup or sync tool that briefly holds the freshly written file. Saves happen on every like, follow, comment and post, so hours-long runs make it likely to hit at some point. Weaker or sloppier models (Haiku, Codex, Gemini CLI) are more likely to blindly retry a failed tool call.
- Scenario: persist() calls fs.renameSync(tmp, file) once, with no retry (graceful-fs/write-file-atomic retry EPERM/EACCES/EBUSY on win32 for exactly this case). recordAction() is called after the real click: browser.ts:2436 for likes and follows, 2475/2477 for comments and DMs, 2486 for posts. Its saveLive(true) then throws 'EPERM: operation not permitted, rename ...marketo-db.json.tmp-1234'. The browser tool returns an error, although Instagram already registered the like or the post is already up, and the post settle hold (2490+) is skipped. The AI retries: a second click on the heart un-likes, a second press on Follow opens or performs an unfollow, and a retried post flow uploads the reel twice.
- Fix: Retry renameSync on EPERM/EACCES/EBUSY with a short backoff (about 1-2 s total). If it still fails, keep the change in memory, log it, schedule a deferred save and never throw out of recordAction/touchLive/saveLive. The action has already happened.
- Skeptic: renameSync at store.ts:147 has no retry. recordAction (browser.ts:2436/2475/2477/2486) would throw after the click if Windows AV or sync software holds the target, and whether that happens is outside behaviour. The claimed consequence is mostly refuted. The counts are raised in memory before persist runs (store.ts:764-784), so limits still hold. A retried click on a pressed Like or an 'Unlike' label is refused at browser.ts:2353-2354 and in the verdicts (1137/1172/1195). Unfollows are their own verdict kind, never a counted follow. What remains: the tool reports an error after a real action, and for a post the settle and upload hold (2490+) is skipped, so a Threads or Facebook upload can be lost.

## Refuted

- The Wizard switches pre-tier installs to the Max tier (Fable, 4 runs a day) and always enables autopilot with Claude Code: The 'max' default only applies to installs that finished setup before tiers existed. Public releases (1.0.0 onward) all have tiers, so very few installs qualify. The tier is also not changed silently: the TierPicker (Wizard.tsx:757) shows the selected tier, so the user sees Max before turning autopilot on. The Codex-only claim is wrong: the toggle refuses to turn on unless Claude Code is connected (line 869, claudeReady) and is labelled 'with Claude Code', so ai:'claude' is the documented behaviour, not a bug.
- With approvals on, an unattended run is told to keep calling the same tool, so it loops indefinitely: It is not indefinite. approvals.wait resolves after 45 s with the current state, and sweep marks a pending request 'expired' after PENDING_TTL_MS (10 min). The call that crosses 10 minutes gets 'The approval ... expired unanswered. Ask the user whether they still want it.' (browser.ts 2326), which tells the model to stop, not retry. The autopilot prompt (autopilot.ts 79/675) also says to skip an approval card that is still waiting. At worst there are about 13 retries over 10 minutes per action, and only after the user has switched approvals on (default off). A new loop would need the model to ignore the expired message.
